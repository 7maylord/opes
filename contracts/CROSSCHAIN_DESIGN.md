# Future contract design — bounded crosschain payouts

Status: deferred future feature. The current implementation path uses backend and wallet restrictions for multichain payouts, with the verified Arc same-chain factory/vault/escrow contracts remaining the only OPES contracts in active scope. This document preserves the earlier contract-enforced design for a later version; it is not a prerequisite for backend B0-B9 work. See [future features](../FUTURE_FEATURES.md).

Checked 2026-10-02. The user requires Arbitrum, Base, Arc, Celo, Ethereum and Monad plus their testnets. [Network scope and provider matrix](NETWORK_SUPPORT.md) defines current route capabilities and provider gaps. No deployed crosschain OPES contract support is claimed.

## Route and capability boundary

The reference conversion route is Base native USDC → CCTP V2 Standard Transfer → tenant executor on Arbitrum → Uniswap V3 exact-output swap → the approved recipient. Generalize CCTP sources/destinations to the five supported chain families in the network matrix, and support plain USDC delivery without a swap. Celo requires a separately specified transport before its crosschain routes can execute. There is no mandatory Arc custody hop. The Railway worker obtains quotes/attestations and submits typed transactions; the model proposes a route but has no signing authority.

Use `TokenMessengerV2.depositForBurnWithHook` directly, with finality threshold 2000, a bounded fee and the destination executor as both mint recipient and destination caller. Hook data carries OPES's authorization commitment; it does not automatically execute a swap. The destination executor calls `MessageTransmitterV2.receiveMessage` and later performs the swap. No forwarding service, Fast Transfer, fee-wrapper contract or aggregator is needed for this version. Standard transfers must still quote and bound fees; do not assume they are free. [Circle interfaces](https://developers.circle.com/cctp/references/contract-interfaces)

Select `SwapRouter02.exactOutputSingle`, which provides the one operation needed here. This deliberately uses the published V3 router despite Uniswap recommending Universal Router for general integrations. No arbitrary calldata, multihop paths, Permit2 or router command language enters OPES. The initial route uses fee tier 100; fee tier is part of an owner-approved route and cannot silently change. [Published deployments](https://developers.uniswap.org/docs/protocols/v3/deployments/v3-arbitrum-deployments)

The first implementation offers direct and recurring payouts from a source vault. Crosschain milestone payouts are **disabled**: existing escrows pay their immutable payee in their bound USDC and cannot safely treat an executor as that payee. Reject milestone action codes and escrow-funding keys in the crosschain entrypoint. Keep held allocations, sequential release, cancellation and refund behavior unchanged. Supporting crosschain milestones later requires a separate reviewed escrow lifecycle, including destination completion evidence; do not bridge a normal escrow release and report the milestone settled. This is an explicit initial capability boundary under XC-9, not completion of crosschain milestone support.

## Tenant custody and authorization

Extend the source `BusinessPolicyVault` in C7b and add one `CrosschainPayoutExecutor` per tenant on the destination. The source vault itself calls CCTP, so no extra source adapter or shared custody pool is needed. Each destination executor binds immutable organization, destination chain/domain/USDC, local CCTP messenger/transmitter and recovery address, with tenant roles. Owner-approved immutable source-binding records identify each source chain/domain/vault/token/messenger; these records support multiple sources without multiple destination custody pools. Disable execution without deleting historical bindings needed for receipt/recovery. Never infer a trusted source from a matching organization hash alone. The platform provisioner pays deployment gas but receives no custody role. Start crosschain execution disabled/paused.

Source owner approves immutable route records and recipient/token permissions. A route ID commits to the entire route; disabling a route prevents new authorization/burns. Destination route approval is separate and must be confirmed before source submission. An in-flight message may always be received for recovery even if its route was later disabled; disabled routes cannot swap. Do not overwrite a route record to change existing commitments.

Add a distinct `PAYOUT_AUTHORIZER_ROLE` to the source vault. It may authorize exact intents only within the owner's delegated crosschain limit, approved recipient/token routes and existing spending policy. It cannot execute, administer or recover. Owner and authorizer roles cannot overlap with an operator. Owner approval handles amounts above the delegated limit, while single/vendor/day caps remain mandatory. Defaults grant no authorizer and allow no routes. B6's deterministic verifier uses this separate credential; the model and execution worker never receive it. This is an explicit trust boundary: contracts cannot establish whether an invoice is genuine. A compromised authorizer can approve false obligations within delegated bounds, just as a trusted invoice verifier can; tenant isolation and spending caps still apply.

Every intent is registered before operator execution, including amounts below the ordinary autonomous threshold. Register the approver, owner-at-approval and authorization epoch; owner transfer or revocation invalidates unburned authorizations. Revoking then regranting a role must not revive them. This permits automatic authorization by the deterministic service without letting the operator alter the recipient, amount or route after approval.

Use one reservation for each stable obligation key. Registration rejects used keys and conflicting live reservations and reserves `maxSourceDebit` from available source USDC. Same-chain direct payments, mandate registration/execution, escrow funding and owner recovery must respect these reservations. A burn consumes the existing vault replay key and releases its reservation atomically; failure restores both. Cancellation/expiry cleanup releases only an unburned reservation. A cancelled hash cannot be revived by an operator; replacement requires a new authorized revision. An identical live registration is idempotent and cannot reserve twice.

At burn, recheck live authorization, route policy, available balance, pause, vendor and UTC-day limits. Charge the **actual burn amount** once against source/vendor caps; surplus recovery never replenishes that day's cap. Keep per-obligation replay state permanently consumed after a successful burn. No independent crosschain replay map may bypass `usedIdempotencyKeys`. Approve only the exact burn amount to the fixed CCTP messenger, clear allowance after success, and verify the source balance debit; any failure rolls back replay, reservations, counters and approval consumption. Emit a distinct `CrosschainDispatched` event with intent/key/route and burned amount, never the same-chain settlement event. Destination funding, actual payout and surplus/recovery also use distinct events with asset amounts and the intent hash.

Crosschain recurring mandates bind destination token/recipient, route and exact payout per cycle, plus source-USDC cycle/total ceilings and the existing finite UTC schedule. Each cycle uses its existing obligation key and requires a bounded intent from the authorizer. Check due time, active status and both mandate caps at burn; count burned USDC toward the mandate once. Mandates declare same-chain or crosschain mode at creation, so a cycle cannot be executed through both routes. Cancelling a mandate stops future burns; it cannot undo a completed burn.

## Canonical commitment

Use static Solidity structs with the following field order. All addresses are EVM addresses; every money field is atomic units, never a float. No string ticker, dynamic calldata or quote-provider payload is part of an executable instruction.

| Struct | Ordered fields (Solidity types) |
|---|---|
| `Route` | `uint256 sourceChainId`, `uint32 sourceDomain`, `address sourceVault`, `address sourceToken`, `address sourceMessenger`, `uint256 destinationChainId`, `uint32 destinationDomain`, `address destinationExecutor`, `address destinationUsdc`, `address destinationMessenger`, `address destinationTransmitter`, `address payoutToken`, `uint8 payoutMode`, `address swapRouter`, `address swapFactory`, `uint24 poolFee` |
| `PayoutIntent` | `bytes32 organizationDomain`, `bytes32 obligationKey`, `uint64 revision`, `bytes32 contextHash`, `bytes32 routeId`, `uint8 action`, `bytes32 mandateId`, `uint32 cycleIndex`, `address recipient`, `uint64 payoutAddressVersion`, `address refundRecipient`, `uint256 amountOut`, `uint256 burnAmount`, `uint256 maxSourceDebit`, `uint256 maxBridgeFee`, `uint256 referenceSwapInput`, `uint256 maxSwapInput`, `uint256 maxPoolFee`, `uint16 slippageBps`, `uint256 sourceGasBudgetAtomic`, `uint256 destinationGasBudgetAtomic`, `uint64 validAfter`, `uint64 burnBefore`, `uint64 payBefore`, `uint64 recoverAfter` |

`routeId = keccak256(abi.encode(uint256(1), route))`. `intentHash = keccak256(abi.encode(uint256(1), intent))`. The route hash binds both chains, the source vault and destination executor; the intent additionally binds organization and obligation. These are separate crosschain schema-1 hashes; they must never be accepted by the existing same-chain `approveDecision` path. Hook data is exactly `abi.encode(uint256(1), route, intent)`. Reject trailing bytes, noncanonical encodings, unsupported versions and empty required IDs. Compare the decoded encoding with the received bytes. C7b must add independently generated golden encoding/hash vectors before any execution implementation.

The expanded layout has 16 route fields and 25 intent fields: 1,344 hook bytes and a 1,572-byte burn body. The added payout mode changes the draft hash layout before C7b vectors or deployments exist. Both testnet transmitters reported an 8,192-byte body limit, message/body version 1 and the expected local domain/remote messenger at the recorded blocks. Check these again before deployment; the source revision is a parser reference, not proof that provider proxies cannot change.

Actions are `4 = crosschain direct`, `5 = crosschain recurring`; reject all others. Direct requires zero mandate/cycle fields; recurring requires the stored mandate/key/cycle match. Require source chain/vault/token and organization to match the executing vault, and destination identities to match the approved route. Bind refund recipient to the configured tenant treasury address on the destination chain, never an operator-selected address.

Require positive `amountOut`, `burnAmount` and `maxSourceDebit`, with `burnAmount <= maxSourceDebit` and `maxBridgeFee < burnAmount`. For swap mode require positive reference/max swap input and `maxSwapInput <= burnAmount - maxBridgeFee`. That swap-mode inequality reserves enough destination input even at the approved maximum bridge fee. Require `slippageBps <= 10000` and `maxSwapInput <= ceil(referenceSwapInput * (10000 + slippageBps) / 10000)`, with overflow-safe arithmetic. The reference quote includes pool fees and is validated by the deterministic authorizer; the contract does not treat a caller-supplied quote as an oracle. Token and pool policies may set stricter owner ceilings. These quote/slippage/pool checks apply to swap mode only.

`payoutMode = 0` means exact USDC delivery: require `payoutToken == destinationUsdc`, zero router/factory/pool fee and zero reference/max swap input, pool-fee ceiling and slippage fields; require `amountOut <= burnAmount - maxBridgeFee`. Mode `1` means the reviewed V3 exact-output swap with an output token different from destination USDC. Reject other modes. Both modes preserve exact recipient balance-delta checks, deadlines, replay, surplus and recovery. Reject same-chain and mainnet-to-testnet routes. CCTP domain 0 is valid for Ethereum; unavailable transports never use 0 as a sentinel.

Require `validAfter < burnBefore <= payBefore <= recoverAfter`. Source burns only at `validAfter <= now < burnBefore`; destination swaps only at `now < payBefore`; owner recovery starts at `now >= recoverAfter`. After expiry, receipt of an already-burned transfer remains possible. Never reject a valid mint solely because payout authorization expired.

## Destination authentication and funds

`receivePayout(message, attestation)` is permissionless and nonreentrant. It validates the fixed message format and calls only the immutable Circle transmitter. Set CCTP `destinationCaller` to this executor, so an external account cannot mint around its accounting. Circle verifies the attestation and nonce; OPES additionally checks its own route and payout fields. Require a successful receive return and the expected USDC balance increase before committing a funded record. No swap occurs in this transaction.

Pin the inspected Circle reference revision `a92a2b4e7e6ef99bf0b05dca71780f5ec190e729`. The [header](https://github.com/circlefin/evm-cctp-contracts/blob/a92a2b4e7e6ef99bf0b05dca71780f5ec190e729/src/messages/v2/MessageV2.sol) is 148 bytes before its body; the [burn body](https://github.com/circlefin/evm-cctp-contracts/blob/a92a2b4e7e6ef99bf0b05dca71780f5ec190e729/src/messages/v2/BurnMessageV2.sol) is 228 bytes before hook data. Validate versions against the deployed providers (expected 1), source/destination domains, header sender/recipient = source/destination TokenMessenger, caller = executor, and requested/executed finality >= 2000. Body burn token, mint recipient, amount, message sender, max fee and hook must match a retained owner-approved source binding, the route and intent. **Header sender is Circle's messenger; body messageSender is the OPES vault.** Require `feeExecuted <= maxBridgeFee`, and received delta exactly `burnAmount - feeExecuted`. Attester-populated fields may differ from the initial source message; don't require a hash of all source bytes to equal the final attested message.

Use a small checked Solidity-0.8 parser for this single format, tested against the pinned layout. The upstream libraries target 0.7.6 and depend on TypedMemView; do not add another compiler/toolchain just to parse fixed fields. Validate lengths before slices and require zero upper bytes for every encoded EVM address. This is message decoding; signature verification remains Circle's job.

Store funded amount, intent hash, source domain/nonce and destination status. Reject a second funding record for the same source-chain/source-vault/obligation, and reject duplicate nonces even if hook bytes change. Duplicate submissions reconcile the original record; they never assign another balance. Keep total allocated USDC separate from the raw token balance, so unsolicited deposits cannot subsidize a different payout or be mistaken for a mint. No administrator may sweep allocated funds.

`executePayout(intentHash)` is operator-only, nonreentrant and pause-aware. Read every payment parameter and its mode from the stored commitment. In USDC mode, transfer only the committed USDC amount, check the recipient delta, and mark paid atomically without any approval or router call. The remaining swap-specific steps apply only to mode 1. Verify the approved factory's pool for the bound token pair/fee, approve only `min(allocatedUSDC, maxSwapInput)`, and call `exactOutputSingle` with this executor as recipient and `sqrtPriceLimitX96 = 0` (require the complete exact output). The executor enforces its own deadline because this router's tuple has no deadline. Clear allowance after success, measure actual USDC spent and payout-token received, then transfer exactly `amountOut` to the fixed recipient and check their balance delta. Any failure reverts the swap, transfer and status change together, leaving the earlier mint intact. Reject fee-on-transfer/rebasing output tokens. [Pinned router interface](https://github.com/Uniswap/swap-router-contracts/blob/70bc2e40dfca294c1cea9bf67a4036732ee54303/contracts/interfaces/IV3SwapRouter.sol)

Require the conservative pool-fee bound `ceil(actualInput * poolFee / 1000000) <= maxPoolFee`; this is a cap, not an assertion of the pool's exact rounding. Pool fees are included in actual swap input, not charged again. USDC mode has no pool fee. There is no OPES relayer fee deducted from principal in this version.

After delivery, mark `Paid` and retain unused USDC as a separately claimable surplus belonging to the committed refund recipient. Anyone may trigger that fixed-address refund. A blocked refund address must not revert an otherwise successful recipient payment. For an unpaid funded intent, only the destination tenant owner may recover its entire allocation to the fixed refund recipient after `recoverAfter`, including while paused; mark `Recovered` before transfer, with atomic rollback on failure. Paid and recovered are mutually exclusive. A refund does not imply the payable was settled, and recovery cannot reset the source replay key.

## Worker, gas and accounting

Track source authorization, submission-unknown, burn-confirmed, attestation-pending, receive-submission-unknown, funded, swap-submission-unknown, paid, surplus-pending/refunded and recovered separately. Store chain/hash/nonce/block/log identity per leg. Before every submission reconcile the source replay/dispatch record or destination record; after a timeout query receipts and account nonce before replacement. A pending nonce alone is not proof of successful execution. Poll Circle's V2 attestation endpoint for the source transaction and select the matching burn/message, never merely the first result.

An attestation outage leaves USDC in transit. A stale quote triggers a bounded requote; swap revert leaves funded USDC on the selected destination. Neither causes another source burn. Retry only while the original payout bounds/deadline still hold. Otherwise recover/escalate; a later payment after recovery needs a separately reviewed replacement workflow, not automatic reuse of the original obligation key. Provider outages do not make an unpaid liability disappear.

Gas budgets are native 18-decimal atomic units: ETH on Base/Arbitrum/Ethereum, CELO on Celo, MON on Monad and USDC on Arc. Arc ERC-20 principal uses six decimals over the same native balance, so never sum the two views. Keep sponsor and tenant treasury accounts separate; use CELO gas initially rather than implicitly selecting Celo alternative fee currencies. OPES-funded signers pay it. The intent commits per-chain gas budgets, and the deterministic signing service reserves worst-case transaction cost before signing (including Arbitrum's chain-specific fee estimate), counts failed attempts, and bounds replacement fees against the remaining budget. Exhaustion pauses submission with a visible reason. Contracts cannot cap all gas an external sponsor spends, especially on reverted calls; do not claim they do. No gas reimbursement is withdrawn from customer principal. The signer/sponsor service is the enforcement boundary for these budgets.

Use integer per-asset subledgers. Let `B` = burned USDC, `F` = attested bridge fee, `M = B - F` = received USDC, `S` = actual swap input, `R = M - S` = surplus and `O` = exact payout-token delivery. Reserve `maxSourceDebit` offchain/onchain at authorization; a reservation alone is no accounting expense. At confirmed burn, move `B` from source custody to in-transit assets. At mint, move `M` to destination custody and recognize `F` as bridge fee, clearing transit. At paid receipt, derecognize `S`, record conversion/delivery of `O`, and reduce the accepted payable by its delivered token units. For plain-USDC delivery there is no conversion: use `S = O` in USDC atomic units, reduce destination custody and settle that USDC liability, with `R = M - O`. Refund/recovery changes custody location only. Never post mint or source dispatch as vendor settlement.

For functional-currency entries, B8 must use the organization's configured valuation source/version and the payable's booked carrying value, with rational/fixed-point arithmetic and recorded rounding. Carry bridge inventory at source book cost; allocate that basis proportionally between `F`, `S` and `R`, assigning any rounding remainder to retained inventory. At settlement, post the difference between the payable's carrying value released and input inventory cost to realized FX/conversion gain/loss. Do not separately estimate and deduct the pool fee again: it is embedded in `S`. Sponsor gas is OPES expense per receipt, not a tenant principal deduction. Missing valuation data leaves functional-currency posting pending; it cannot invent a 1:1 rate or block recording factual token movements. Unique `(chain, tx, log, posting-kind)` and `(organization, obligation, settlement)` constraints prevent duplicate postings. Reorg corrections use reversals, not deletion or balancing plugs.

## Deployment and migration

The already verified Arc factory embeds the same-chain vault/escrow creation code and cannot acquire new methods. Keep its manifest and ABI version binding intact. C7b changes require a new versioned factory deployment for new source vaults and a separately verified destination executor deployment path; verify code-size/initcode limits again. Export all new contract and provider-interface ABIs to both existing application ABI directories using `ExportAbis.mjs`; no inline application ABI fragments.

B2 records environment, chain, factory version, source-binding records and tenant addresses before activation. Deploy the paused source vault first, bind the destination executor to that actual address, establish owner-approved source/destination routes, then enable the source capability. Owners must explicitly migrate any existing funds/mandates. Pause and revoke the old operator, reconcile pending transactions and partition obligations before enabling a replacement source. An immutable Arc vault cannot authorize Base funds, and matching organization hashes across chains are not a global replay lock. B6/B7 must enforce one selected settlement source per obligation using database uniqueness and transactionally reserved state; contracts enforce replay within that source. Do not promise protection against an owner/authorizer deliberately authorizing the same obligation across independent vaults.

## Implementation gates and acceptance

| Requirement | Concrete check before enabling the route |
|---|---|
| XC-1 | Approved direct and due recurring obligations progress through the worker without manual bridge/swap steps. Milestone routing is visibly unsupported. |
| XC-2 | Check chain/domain, decimals, provider code/source, token variant acceptance, pool identity and test-token labeling. No testnet target/pool means route disabled. |
| XC-3 | Independent encoding vectors; mutate every committed field; revoked approver/owner epoch; duplicate reservations; same-chain/crosschain key collisions; policy limits at burn. |
| XC-4 | Operator cannot authorize itself or submit router calldata; authorizer has no execution/recovery powers; typed provider calls only. |
| XC-5 | Real-provider quote/fork checks and testnet funded-pool proof; quote change cannot exceed committed input, fees or expiry. |
| XC-6 | Wrong domains, header sender, body sender, recipient/caller, token, version, finality, amount, fee, attestation or hook fail; swap+delivery rollback together. |
| XC-7 | Restart/timeout at every leg, delayed attestation, duplicate mint/pay, nonce replacement, expiry after burn, paused mint recovery and swap revert after mint; source burn count stays one. |
| XC-8 | Conservation `B = F + S + R`; outstanding allocation protected from sweeps/donations; blocked refund; gas exhaustion; integer valuation/rounding and posting uniqueness. |
| XC-9 | Due/cancelled/expired/wrong-mode recurring cycles; milestone/funding keys fail closed; existing escrow hold/refund and same-chain tests still pass. |
| XC-10 | Two-tenant adversarial calls, recipient balance proof, malicious/reentrant tokens/router, empty liquidity, false returns, all exclusive deadline boundaries and code-size gates. |

C7b checkpoints: twelve-network capability validation and canonical types/hash vectors → source authorization/reservations and direct burn → destination authenticated receipt → plain-USDC and exact-output delivery/recovery → multi-source isolation → recurring mode integration → versioned provisioning and ABI export. Each money-moving checkpoint includes its own failure tests and commit; intermediate contracts remain disabled for live custody. C7c adds provider-fork and contract-leg integration evidence; actual worker crash/restart validation belongs to B7/B10 before live application enablement. Source-code presence and a quote are insufficient to mark C7c complete. No contracts were deployed or packages installed during C7a.

The expanded C7a scope is not fully closed: finish the Celo-specific bridge design and verify missing destination swap deployments before enabling those capabilities. CCTP and same-chain work can proceed independently; those open items do not remove Celo or any of the twelve environments from the required product scope.
